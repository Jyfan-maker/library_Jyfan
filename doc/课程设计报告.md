## 一、需求分析

本系统面向学校图书馆或小型书店，用于管理图书信息与读者借阅记录。系统把课堂上学到的关系模型、SQL、完整性约束、事务与索引等知识点串成一条完整的数据流，最终落到一个能登录、能增删改查、能看见数据变化的可运行系统上。

## 二、数据库设计

### 2.1 E-R 图

系统包含 4 个业务实体（用户、分类、图书、借阅）和 1 个辅助表（sqls）。实体联系如下：

- 分类 1 : N 图书（一本图书属于一个分类）
- 用户 1 : N 借阅（一条借阅记录属于一个读者）
- 图书 1 : N 借阅（一条借阅记录对应一本图书）

读者与图书之间的"借阅"是多对多关系，通过 borrow 借阅表分解为两个一对多关系，这是关系数据库设计的经典手法。

### 2.2 关系模式

```
users(id, username, password, real_name, role, phone, created_at)
category(id, name, remark, created_at)
book(id, title, author, isbn, category_id, price, stock, created_at)
borrow(id, user_id, book_id, borrow_at, return_at, status, fine, remark)
sqls(id, sqlb, remark)
```

其中下划线主键：users.id、category.id、book.id、borrow.id、sqls.id。
外键：book.category_id → category.id；borrow.user_id → users.id；borrow.book_id → book.id。

### 2.4 设计说明（老师可能提问的点）

**为什么分类要独立成表？** 若像简单实现那样把 category 作为 book 里的字符串字段，同一分类名会在多本书中重复存储，产生数据冗余，违反第三范式。独立成表后分类名只存一次，book 只存 category_id 外键，满足 3NF。

**金额为什么用 DECIMAL？** 浮点数（FLOAT/DOUBLE）存在精度误差，59.80 可能存成 59.799999，金额计算必须精确，故用 DECIMAL(10,2)。

**三组外键的意义？** fk_book_category 保证图书分类真实存在；fk_borrow_user 与 fk_borrow_book 让借阅记录必须对应真实读者和图书，并配合 ON DELETE RESTRICT 阻止删除仍有借阅记录的图书或仍有图书的分类。

**索引考虑？** 为高频查询列建索引：book.title、book.author 用于 LIKE 模糊搜索；book.category_id 用于分类统计；borrow.user_id、borrow.book_id 用于按读者/图书查借阅；borrow.status 用于筛选在借记录；users.username 因 UNIQUE 约束自带唯一索引，登录按它查询很快。

**初始数据规模？** 12 个分类、124 本互不重复的图书（涵盖计算机、文学、历史、经济、哲学、自然科学、教育、艺术、工程、法律、医学、外语共 12 类），4 个用户，5 条借阅示例，25 条 SQL 模板。

## 三、系统实现

### 3.1 技术栈

| 层次 | 技术 |
| :--- | :--- |
| 数据库 | MySQL，utf8mb4，独立库 library_Jyfan |
| 服务端 | Java 8 目标 + Spring Boot 2.7.18 + JdbcTemplate |
| 前端 | 原生 HTML + CSS + JavaScript（fetch 发 JSON） |
| 通讯 | 请求/响应均为 JSON，统一 `{code, msg, data}` 格式 |

### 3.2 核心实现思想

**（1）SQL 与代码分离 + 集中管理**
所有业务 SQL 存在数据库的 sqls 表（id 存 key，sqlb 存语句）。服务启动时由 Init 组件把全表加载进全局 Map（Init.sqlmap），业务代码只按 key 取用。唯一硬编码的 SQL 是加载用的 `SELECT id, sqlb FROM sqls`。好处：改 SQL 只改库、重启即可，不用改代码或重新编译。

**（2）独立 SQL 访问类**
Sql 类（@Repository）统一封装 update / insert / one / list / rows 方法，全部参数化（PreparedStatement），禁止字符串拼接用户输入，有效防止 SQL 注入。

**（3）数据库直接拼 JSON**
查询类 SQL 用 MySQL 的 JSON_OBJECT / JSON_ARRAYAGG 直接把结果拼成 JSON 字符串，后端拿到后原样返回给前端，不做对象映射。空列表用 IFNULL(..., JSON_ARRAY()) 兜底。

**（4）登录与 MD5**
密码在数据库中只存 MD5 密文（如 123456 → e10adc3949ba59abbe56e057f20f883e）。登录时服务端先把输入密码算 MD5 再与库中密文比对，前端与数据库都不出现明文。登录成功后把 uid/uname/role 写入 HttpSession。

**（5）登录态校验**
未登录访问业务接口返回统一 `{code:401, msg:"未登录或会话已过期"}`，前端 api.js 的 handle() 识别到 401 自动跳转登录页。

**（6）事务处理（加分项）**
借书用 `@Transactional` 把"新增借阅记录"与"库存减一"包在同一事务；还书把"更新状态"与"库存加一"包在同一事务，保证数据一致性。

### 3.4 关键代码说明

SQL 访问类（comm/Sql.java）核心方法：

```java
public int update(String key, Object... args) {
    return jdbc.update(text(key), args);   // text(key) 从全局 Map 取 SQL
}
public String one(String key, Object... args) {
    return jdbc.queryForObject(text(key), String.class, args);  // 返回数据库拼好的 JSON
}
```

借书事务（web/BorrowController.java）：

```java
@PostMapping("/borrow")
@Transactional(rollbackFor = Exception.class)
public Map<String, Object> borrow(...) {
    int dec = sql.update("book_stock_dec", bookId);  // 库存减一（stock>0 才成功）
    if (dec == 0) return R.fail("库存不足，无法借阅");
    int id = sql.insert("borrow_add", uid, bookId);  // 新增借阅记录
    if (id <= 0) throw new RuntimeException("借书记录新增失败，事务回滚");
    return R.ok(id);
}
```

## 五、总结

本次课程设计完成了一个可运行的图书管理系统。数据库方面，独立建库 library_Jyfan，设计了 5 张表、3 组真实外键，满足第三范式，并准备了 124 本不重复图书的初始数据；服务端方面，采用 Spring Boot + JdbcTemplate，实现了 SQL 与代码分离、SQL 集中管理、参数化查询、MD5 密码、统一返回、登录态校验以及借还书事务；前端方面，用原生 JavaScript 实现了登录、图书/分类/借阅管理与统计报表的完整交互。

遇到的问题与解决：一是所用 MySQL 26.7 版本没有内置 MD5() 函数，改为在初始化脚本中直接写入固定的 MD5 密文常量，兼容各版本；二是 SQL 存入 sqls 表时若双重转义单引号会导致运行时语法错误，改为只转义一次；三是高版本 JDK 编译 Java 8 目标有警告但不影响运行。

尚未完成的部分：逾期罚金仅预留字段，未实现按日期自动计算；分页在前端做简单实现，服务端未做物理分页。这些可作为后续扩展方向。

通过本次设计，我把课堂上分散的关系模型、SQL、完整性约束、事务与索引等知识点串成了一条完整的数据流，对"浏览器—服务端—数据库"三层之间的数据流转有了切身体会，也建立了密码不明文、接口校验登录态、SQL 参数化等基本安全意识。
